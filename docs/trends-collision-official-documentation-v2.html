03 Executive summary

What we are building.

The product is a collision repair workflow platform that combines a public website, internal operations system, customer vehicle tracker, and digital jacket workflow.

Architecture decision

Build one modular monolith using Next.js App Router, React, TypeScript, Prisma, Neon Postgres, Node.js runtime, and vanilla CSS.

Primary system object

The repair order is the center of the platform. It connects customer/dealer, vehicle, workflow, stages, assignments, forms, supplements, notifications, and audit logs.

Major revision

The app must support configurable workflow templates. Insurance vehicles, dealer vehicles, COD jobs, and internal jobs should not be forced into one hardcoded stage path.

The MVP should not attempt to replace estimating software, insurer systems, billing systems, or parts procurement on day one. The first version should solve daily workflow clarity: where the vehicle is, what stage it is in, what paperwork is complete, what is blocking progress, and who owns the next action.

04 MVP product definition

What is in scope and what is not.

This scope keeps the MVP focused enough to build, while still covering the real workflow needs confirmed during discovery.

Website + trust

Public website, services, certifications, how to file a claim, contact funnel, customer tracker entry.

Internal operations

Staff login, roles, departments, repair orders, workflow templates, stages, assignments, red flags.

Digital workflow

Digital jackets, intake forms, signatures, damage diagrams, supplements, customer portal tokens, activity logs.

Email delivery

Logged customer updates can exist first. Email delivery can be added once message templates are approved.

Basic attachment upload

Photos and scanned files are useful, but storage integration can be phased after structured data is stable.

Basic reporting

Simple dashboards should exist. Advanced analytics should wait for real usage data.

Native app

Responsive web is enough for the MVP. Native iOS/Android should wait.

CCC One integration

Only add if official access and stable integration requirements are confirmed.

External portals

Dealer and insurance self-service portals should come after internal workflow is proven.

11 System rules

Rules developers cannot break.

These rules should be enforced in services, tests, and code reviews.

!
Never expose internal notes.The portal must use a customer-safe DTO assembled separately from internal repair order detail.
!
Use tokenized access.The customer tracker must use CustomerPortalToken, never a raw repair order ID.
!
Show only approved stages.The tracker can only show stages where customerVisible is true.
!
Respect revoked or expired tokens.Expired or revoked portal tokens must return no repair data.
!
Every repair order must have a job type.Job type drives the workflow template and stage generation.
!
Stages are generated from templates.Do not hardcode one universal workflow path in the UI or API.
!
Stage moves create history.Every stage transition must write RepairStageHistory and ActivityLog.
!
Skipped stages must be explicit.Skipped steps should be saved as SKIPPED with actor, timestamp, and optional reason.
!
Legal text must be versioned.Signed forms must preserve the exact template version shown to the signer.
!
Finalized docs are immutable.Do not silently edit finalized legal documents. Void or create a new version.
!
Signatures need metadata.Store signer name, timestamp, signature artifact, IP if available, and user agent if available.
!
Damage diagrams are structured.Store marks as coordinates and metadata, not only as a flattened image.
!
Important mutations log activity.Create activity rows for repair order changes, documents, stages, assignments, supplements, alerts, and customer updates.
!
Actor and timestamp are required.Every activity should store actorUserId if available and a reliable timestamp.
!
Account scoping is mandatory.Every business query should be scoped by accountId, even in single-shop MVP.
!
Customer visibility is explicit.Never infer that a note or stage is customer-safe unless it is marked as such.

13 Database schema

Schema explorer and implementation outline.

The schema is designed for a single-shop MVP with future multi-location or multi-tenant readiness through accountId scoping.

Model explorer

Critical Prisma concept 
model WorkflowTemplate {
  id          String   @id @default(cuid())
  accountId   String
  name        String
  jobType     JobType
  isDefault   Boolean  @default(false)
  isActive    Boolean  @default(true)
  stages      WorkflowTemplateStage[]
}

model WorkflowTemplateStage {
  id                 String @id @default(cuid())
  workflowTemplateId String
  departmentId       String?
  name               String
  customerVisible    Boolean @default(false)
  sortOrder          Int
  redFlagHours       Int?
  canSkip            Boolean @default(true)
}

model RepairOrderStage {
  id              String      @id @default(cuid())
  repairOrderId   String
  departmentId    String?
  name            String
  status          StageStatus @default(NOT_STARTED)
  sortOrder       Int
  startedAt       DateTime?
  completedAt     DateTime?
  assignedToId    String?
  customerVisible Boolean     @default(false)
}

14 API reference

REST-like route handler map.

The MVP should expose a stable internal API contract. Some form mutations can use server actions, but route handlers should remain available for future mobile, integrations, and portal flows.

Example endpoint specification: POST /api/repair-orders
Request body
{
  "customerId": "cus_123",
  "vehicleId": "veh_123",
  "dealerId": null,
  "jobType": "INSURANCE",
  "workflowTemplateId": "wft_insurance_default",
  "claimNumber": "ABC12345",
  "promisedDate": "2026-07-30T17:00:00.000Z"
}
Side effects
1. Validate authenticated user permission.
2. Create RepairOrder.
3. Generate RepairOrderStage rows from selected WorkflowTemplate.
4. Create CustomerPortalToken if customer-visible.
5. Create ActivityLog row.
6. Return repair order detail DTO.

17 Testing strategy

Quality plan for launch.

The MVP should include unit, integration, and end-to-end tests for the flows that matter most to the shop.

Unit tests

Permissions, workflow generation, stage transition rules, red flag timing, token validation, and document finalization rules.

Integration tests

Create repair orders, generate stages, move stages, create supplements, finalize documents, and fetch portal data by token.

E2E tests

Front office intake, digital jacket, customer tracker, technician stage update, manager red flag resolution, and print summary.
